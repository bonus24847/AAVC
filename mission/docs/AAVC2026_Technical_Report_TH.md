## บทสรุปผู้บริหาร (Executive Summary — 10 คะแนน)

ทีมของเราส่ง **ควอดคอปเตอร์อัตโนมัติที่ใช้ PX4** หนึ่งลำ ทำภารกิจส่งสัมภาระไข่ไก่สด
(เปราะบาง) หนึ่งฟองต่อหนึ่งเที่ยวบิน (sortie) ลงบนแท่นลงจอด (landing pad) ที่มี ArUco marker
ตรงกับหมายเลขที่กรรมการกำหนดให้ ณ สนามจริง IAAI สจล. และทำซ้ำได้สูงสุด 4 แท่น
ภายในกรอบเวลาปฏิบัติการ (operation window) 20 นาที — ตามภารกิจ AAVC 2026 (V1.3)

ปรัชญาการออกแบบคือ **"เร็วแต่ปลอดภัย และคาดเดาได้" (fast-but-safe determinism)**:
ระบบวิชันแบบดั้งเดิม (classical computer vision — ไม่มี machine learning ในลูปการบิน
และไม่มีการใช้เครือข่ายใด ๆ ซึ่งตามกติกาการใช้เครือข่ายคือการถูกตัดสิทธิ์ทันที)
ขับเคลื่อน flight controller Pixhawk 6X ผ่านคอมพิวเตอร์ร่วม (companion computer)
Raspberry Pi CM4 อากาศยานบินตามเส้นทางบังคับ (transit corridor) P1→P2→P3 ที่ระดับ
20 เมตรอย่างเคร่งครัด กวาดค้นหาพื้นที่ search area เฉพาะเมื่อยังไม่รู้ตำแหน่งแท่นเป้าหมาย
แล้วร่อนลงเหนือแท่นที่ถูกต้องเป็นขั้นระดับความสูง (altitude rungs) ที่ตรวจสอบทุกขั้น
**ลงจอดบนแท่น แล้วจึงปล่อยไข่หลังยืนยันการแตะพื้น (touchdown) เท่านั้น** —
ไข่จะไม่ถูกปล่อยกลางอากาศเด็ดขาด เพราะเกณฑ์ให้คะแนนนับเฉพาะไข่ที่สมบูรณ์และวางบนแท่น
ไข่ที่แตกได้ศูนย์คะแนน

ตำแหน่งแท่นส่งของไม่เป็นที่รู้ล่วงหน้าตอนบินขึ้น กรรมการบอกเพียงหมายเลข marker ต่อเที่ยวบิน
ระบบจึงใช้ **การค้นหาด้วยภาพแบบไม่รู้ตำแหน่งล่วงหน้า (blind visual search) ร่วมกับทะเบียนแท่น
ข้ามเที่ยวบิน (cross-sortie pad registry)** — แท่นทุกแท่นที่เห็นระหว่างการกวาดครั้งแรก
จะถูกถอดรหัสและจดจำไว้ เที่ยวบินถัด ๆ ไปจึงบินตรงเข้าแท่นได้เลยโดยไม่ต้องกวาดซ้ำ
ประหยัดเวลาในกรอบ 20 นาที

ผลการทดสอบยืนยันหลัก (SITL ภารกิจเต็ม 4 เที่ยวบินบนภูมิประเทศสนาม KMITL
บินด้วยคอนฟิกการบินสุดท้าย — กล้อง nadir OV9281 ตัวเดียว และชุดอัตราขยาย (gains)
จากโมดูล System-ID):

| ตัวชี้วัด | ผลลัพธ์ (G4 confirmation run ล่าสุด, tuned gains, SEED 7) |
|---|---|
| ไข่ส่งถึงแท่นที่ถูกต้องตามหมายเลขที่กำหนด | **4 / 4** — ยืนยันหมายเลขโดย verifier, จุดปล่อยห่างจากศูนย์กลางแท่นจริง 0.10–0.30 ม. และลงจอดก่อนปล่อยทุกครั้ง |
| จุดพิกัด transit ที่ทำคะแนน (ไป-กลับ) | **24 / 24** (พลาด 0 จุด) |
| การกลับมาลงจอดที่จุด L&R | 4 / 4 ภายในระยะ 2.6–2.7 ม. จากจุด L&R |
| เวลาที่ใช้ในกรอบปฏิบัติการ (4 เที่ยวบิน) | **1001 วินาที ≈ 16.7 นาที** (< 1200 วินาที) |
| วินัยความสูง | สูงสุด 20.33 ม. — ต่ำกว่าเส้นเตือน 20.5 ม. ไม่มี flag เพดานบิน |
| คำตัดสินของ verifier | **PASS — ผ่าน 19 รายการตรวจ, 0 คำเตือน** (`tools/verify_flight.py` แบบ fail-closed) |

การทดสอบยืนยันก่อนหน้า (committed แล้วทั้งหมด): layout เดียวกันบินก่อนจูน gains
ปล่อยที่ 0.05–0.26 ม.; เที่ยวบินทดสอบบนเฟรมภาพขาวดำ (grayscale) พิสูจน์ pipeline
โมโนโครมแบบครบวงจร (0.14 ม.); confirmation run ของ V1.3 (SEED 42) ส่ง 4/4 ที่
0.10–0.32 ม. พร้อมบันทึกภาพ 1,174 เฟรม JPEG; และ layout สุ่มก่อนหน้าอีก 5 ชุด
ส่งครบ 4/4 ทุกชุดด้วย verifier PASS 0-warn — ดูภาคผนวก ข.

ซอฟต์แวร์ผ่านการเสริมความทนทาน (hardening) ต่อโหมดความล้มเหลวเชิงปฏิบัติการที่สำคัญ
กับโดรนจริงเหนือสนามจริง ได้แก่ เส้นทางตัดมอเตอร์ฉุกเฉิน ("kill") จากสถานีภาคพื้น,
ตัวป้องกันภาพค้าง (camera-freeze guard) ระหว่างบินที่กันการลงจอดบนภาพเก่า,
**เกตลงจอดแบบต้องเล็งกึ่งกลางในขั้นสุดท้าย (centred-final-rung LAND gate)**
ที่ปฏิเสธการลงจอดเยื้องศูนย์ (ไต่กลับ เลื่อนออก แล้วเข้าใหม่ — ไม่ยอมเสียไข่กับการลงจอดที่ไม่ดี),
failsafe ระดับ flight controller สำหรับ RC-loss และแบตเตอรี่ที่ pin ค่าและอ่านกลับตรวจสอบ,
และการบันทึกภาพถาวรตามข้อกำหนด "record **and** transmit" ของกติกา
การทดสอบอัตโนมัติทั้ง 239 รายการผ่านครบ; แกนซอฟต์แวร์การบินเป็นแบบ deterministic
และ offline ทั้งหมด

## 2. การพัฒนาแนวคิด (Concept Development — 30 คะแนน)

### 2.1 พารามิเตอร์ขีดความสามารถที่สกัดจากโจทย์ปฏิบัติการ

สภาพแวดล้อมปฏิบัติการเป็นตัวกำหนดกรอบการออกแบบ จากกติกา (V1.3) และภูมิประเทศสนาม
IAAI KMITL เราสกัดขีดความสามารถที่อากาศยานต้องมี ดังนี้:

| ตัวขับจากสภาพแวดล้อม / กติกา | ค่า | ความต้องการของอากาศยานที่ตามมา |
|---|---|---|
| ห้วงอากาศควบคุม (geofence) | ~296 × 167 ม. | ระยะเวลาบิน + ความเร็วพอครอบคลุมภายในกรอบเวลา |
| พื้นที่ค้นหา (search area) | ~210–227 × 57–74 ม. | บินกวาดครอบคลุมพื้นที่ ~1.3 เฮกตาร์ |
| ระดับ transit (บังคับ) | **20 ม. เคร่งครัด** | รักษาระดับที่ 20 ม. AGL อย่างแม่นยำ |
| แถบความสูงช่วงค้นหา | 10–20 ม. AGL | ภาพที่ถอดรหัส marker ได้จากระดับ 10–20 ม. |
| การร่อนลงส่งของ | ต่ำกว่า 10 ม. ได้เฉพาะเหนือแท่น | การร่อนลงช่วงปลายแบบแม่นยำ + ลงจอดบนแท่น |
| แท่นลงจอด | สี่เหลี่ยมขาว 1 ม., วงแหวน ⌀750 มม., **ArUco 400 มม.** (DICT_4X4_50, หมายเลข 1–6) | ถอดรหัส marker 400 มม. จากแถบความสูงค้นหา |
| กรอบเวลาปฏิบัติการ | 20 นาที, ≤4 แท่น, ปรับคะแนนต่อนาทีถ้าเกิน | ≤ ~5 นาที ต่อเที่ยวบินส่งของเต็มรูปแบบ |
| สัมภาระ | ไข่ไก่สดเบอร์ 0 หนึ่งฟองในกล่องรูปหัวใจ (~16 × 7 × 18 ซม., กระดาษ 300 แกรม) | ช่องบรรทุก + กลไกปล่อยแบบนุ่มนวล; มวล ~[ไข่+เปล] |
| ลิมิต MTOW | ≤ 25 กก. รวม | มีมาร์จินสบาย (ควอดตัวเล็กลำเดียว) |
| ไม่มี RTK GPS | ความคลาดเคลื่อน ~0.5–1.5 ม. | วิชันเป็นเจ้าของ "เมตรสุดท้าย" ไม่ใช่ GPS |

**เรขาคณิตของการถอดรหัสเป็นตัวกำหนดกล้องและความสูงกวาด** — ArUco marker ขนาด 400 มม.
มีขนาดปรากฏ ≈ 18 พิกเซล ที่ความสูงกวาด 12 ม. บนเซนเซอร์ nadir กว้าง 1280 พิกเซล —
เพียงพอสำหรับการถอดรหัสที่เชื่อถือได้เมื่อใช้ ROI up-scale แต่ก็เฉียดลิมิต
ข้อนี้จึงกำหนดให้กล้อง nadir ตัวเดียวต้องกว้าง **1280 พิกเซล** (Meige OV9281,
1280 × 720 โมโนโครม global shutter บนฐาน gimbal กันสั่น — สมการความกว้างแนวกวาดใช้เฉพาะ
ความกว้างภาพ) และกำหนดความสูงกวาดที่ ~12 ม. แทนที่จะเป็นเพดาน 20 ม.

**งบเวลาในกรอบ 20 นาทีเป็นตัวกำหนดระยะเวลาบินและความเร็วกวาด** — สี่เที่ยวบินเต็มใน
20 นาที หมายถึง ≈ 5 นาทีต่อเที่ยว (transit ไป-กลับ + กวาด + ส่งของ + ลงจอด + เติมสัมภาระ)
ทะเบียนแท่นข้ามเที่ยวบิน (§2.3) ตัดการกวาดออกจากเที่ยวบินที่ 2–4
กรอบเวลาจึงผ่านแบบสบาย (วัดจริงใน SITL ≈ 17 นาที)

### 2.2 ระบบส่งของที่เลือก — โครงแบบและสถาปัตยกรรม

**โครงแบบอากาศยาน: มัลติโรเตอร์ลำเดียว (quad-X)** — กติกาบังคับ VTOL เพราะสนามเป็น
พื้นที่เมืองจำกัด; quad-X คือโครงแบบที่ง่ายที่สุดที่ (ก) ลอยตัว (hover) อย่างแม่นยำเหนือแท่น
1 ม. (ข) ร่อนลงแนวดิ่งเพื่อลงจอดบนแท่น และ (ค) ไม่ต้องมีตรรกะการเปลี่ยนโหมดบิน (transition)
การใช้อากาศยานลำเดียว (แทนที่จะเป็นคู่ค้นหา+ส่งของแบบร่วมมือ) ทำให้มวล ต้นทุน
และพื้นผิวความล้มเหลว (failure surface) ของระบบเล็ก ในขณะที่ยังทันกรอบเวลาด้วยกลยุทธ์ทะเบียนแท่น

**สถาปัตยกรรมระบบ (อากาศ + ภาคพื้น):**

```
AIR SEGMENT (ส่วนอากาศ)                        GROUND SEGMENT (สถานีภาคพื้น GCS)
┌──────────────────────────────┐              ┌───────────────────────────┐
│ Pixhawk 6X (PX4)  ── ควบคุม   │  telemetry   │ เทอร์มินัลหลัก (แล็ปท็อป)   │
│   การบิน, failsafes, geofence │◄────────────►│  + Svelte dashboard       │
│      ▲  MAVLink (UART)        │  ≥500 m LOS  │  (แผนที่สด, กล้อง,          │
│      │                        │              │   GO ต่อเที่ยวบิน, KILL)    │
│ Raspberry Pi CM4 (companion)  │              │ RC นักบินนิรภัย (ELRS)      │
│   mission orchestrator,       │  ภาพ          │ เสาสื่อสาร + ไฟสำรอง        │
│   vision, safety watchdog     │─────────────►│ จอแสดงผลภายนอก ≥1 จอ       │
│   ▲ OV9281 nadir 1280×720     │              └───────────────────────────┘
│     (mono GS, gimbal servo)   │
│   optical flow + rangefinder  │   ← ล็อกตำแหน่งสำหรับ "เมตรสุดท้าย" แบบไม่มี RTK
│   เซอร์โวปล่อยไข่ (AUX9)       │
└──────────────────────────────┘
```

สแต็กบริหารการบินเป็น **สถาปัตยกรรมโอเพนซอร์สที่ไม่ใช่กรรมสิทธิ์ปิด** (PX4 บน
Pixhawk 6X) ที่ทีมอินทิเกรตเอง — สอดคล้องกับข้อห้ามของกติกาเรื่องชุดควบคุมการบิน
สำเร็จรูปแบบปิด ส่วนระบบอัตโนมัติระดับสูง (ค้นหา ระบุเป้า หาพิกัด ลงจอด-ปล่อย)
รันบน CM4 เป็นโค้ดคลาสสิกแบบ deterministic

**เหตุผลของการตัดสินใจหลัก:**
- *ใช้ classical CV ไม่ใช่ ML ในลูปการบิน* — เป้าหมายเป็น fiducial marker (ArUco)
  การถอดรหัสด้วย OpenCV มาตรฐานจึงแม่นยำแบบ deterministic ประหยัด CPU บน CM4
  และตรวจสอบย้อนหลังได้ ไม่มี torch/YOLO/VLM ไม่มีคลาวด์ ไม่มีเครือข่าย (เครือข่าย = ตัดสิทธิ์)
- *ลงจอดบนแท่น + ปล่อยหลังแตะพื้น (land-ON + touchdown-gated release)* —
  เกณฑ์คะแนนให้รางวัลกับ "ลงจอดบนแท่น **ก่อน** ปล่อย" และไข่ที่สมบูรณ์
  การปล่อยกลางอากาศเสี่ยงไข่แตกได้ศูนย์คะแนนสัมภาระ การปล่อยจึงถูกล็อกไว้หลัง
  การยืนยันแตะพื้นเท่านั้น
- *ทะเบียนแท่นข้ามเที่ยวบิน* — กรรมการกำหนดแท่นทีละเที่ยวบิน การจดจำแท่นทุกแท่น
  ที่เห็นในการกวาดครั้งแรกเปลี่ยนเที่ยวบิน 2–4 ให้เป็นการบินตรง ซื้อมาร์จินเวลา
- *วิชันเป็นเจ้าของเมตรสุดท้าย* — เมื่อไม่มี RTK ค่า GPS แกว่ง ~0.5–1.5 ม.
  ใหญ่กว่าแท่น 1 ม.; กล้อง nadir + optical flow/rangefinder เป็นผู้ปิดการร่อนลงช่วงปลาย

### 2.3 แนวคิดปฏิบัติการ (mission profile + ยุทธวิธี)

แต่ละเที่ยวบินปฏิบัติตามโปรไฟล์ Fig. 4 ของกติกาในรูปแบบ state machine แบบ deterministic
(`orchestrator/mission.py`):

```
PREFLIGHT (เกต GO ต่อเที่ยวบิน: ผู้ควบคุมยืนยันหมายเลขแท่น + ยืนยันไข่พร้อม)
  → TAKEOFF (ติดอาวุธ ไต่ขึ้น 20 ม. ที่จุด L&R)
  → TRANSIT_INGRESS  P1 → P2 → P3  @ 20 ม.   (ทำคะแนนต่อจุดพิกัด)
  → SEARCH   (เฉพาะเมื่อแท่นเป้าหมายยังไม่อยู่ในทะเบียน:
              บินกวาดแบบไถนา (boustrophedon) เหนือ search polygon @ ~12 ม.
              ถอดรหัสแท่นทุกแท่นที่เห็นเข้าทะเบียนข้ามเที่ยวบิน)
  → LOCALIZE (ร่อนลงเหนือแท่นเป้าหมายเป็นขั้นระดับความสูงที่ตรวจสอบทุกขั้น;
              แท่นหมายเลขผิดจะไม่มีวันชี้นำการร่อนลง)
  → LAND     (ลงจอดบนแท่น; ค่าคลาดเคลื่อนขั้นสุดท้าย 0.2 ม. บนแท่น 1 ม.)
  → DROP     (ปล่อยไข่หลังยืนยันการแตะพื้นเท่านั้น; ถ้าลอยอยู่ให้ข้าม)
  → TRANSIT_EGRESS  P3 → P2 → P1  @ 20 ม.    (ทำคะแนนต่อจุดพิกัด)
  → LAND ที่ L&R  → DISARM (ทีมเติมสัมภาระเข้าได้) → เที่ยวบินถัดไป
```

**ยุทธวิธีค้นหา-ระบุเป้า** — เที่ยวบินที่หมายเลขเป้าหมายยังไม่อยู่ในทะเบียนจะบิน
**กวาดแบบไถนา (boustrophedon / lawn-mower)** เหนือ polygon ของพื้นที่ค้นหา
ถอดรหัสแท่นทุกแท่นที่เห็นเข้าทะเบียนที่จัดเก็บตามหมายเลข marker พร้อมการยืนยันแบบ
k-vote (กันการถอดรหัสผิดครั้งเดียว) การกวาดจะทำจนจบ (หยุดก่อนได้เฉพาะเมื่อยืนยันแท่น
ครบทุกแท่นแล้ว) เที่ยวบินถัดไปจึงบิน **ตรง** เข้าแท่นในทะเบียนโดยไม่ต้องกวาด
แท่นขาวที่ยังถอดรหัสไม่ได้จะถูกบินกลับไปอ่านซ้ำที่เพดานล่าง 10 ม.
ส่วนแท่นที่ถอดรหัสได้แล้วแต่ vote ยังไม่ครบ จะได้การบินแวะเติม vote แบบประหยัด
แทนการกวาดใหม่ทั้งรอบ

**ยุทธวิธีส่งของ (land-ON, touchdown-gated)** — เหนือแท่นเป้าหมาย อากาศยานร่อนลง
ผ่านขั้นระดับความสูง (12 → 8 → 5 → 3 → 2 → 1.5 ม.) โดยเล็งกึ่งกลาง marker ที่ถอดรหัสได้
ใหม่ทุกขั้นด้วยค่าคลาดเคลื่อนที่บีบลงเรื่อย ๆ (จนถึง **0.2 ม.** ก่อนสั่ง LAND —
หนึ่งในสามของแท่น 1 ม.) ตัวควบคุมช่วงปลายจะปฏิเสธการลงจอดถ้า
**ไม่เคยถอดรหัสหมายเลขที่กำหนดได้จริงระหว่างเข้าหา** (เกต id-verified LAND);
แท่นหมายเลขผิดหรือก้อนขาวที่ยังถอดรหัสไม่ได้อาจชี้นำการร่อนได้ แต่ไม่มีวันทำให้ไข่ถูกปล่อย
ขั้นสุดท้ายยังต้อง **ล็อกเป้าได้จริง**: ถ้าการเล็งกึ่งกลางไม่ลู่เข้าใน 0.2 ม.
(เช่น สตรีมพิกัดภาพเอนเอียงที่ความสูงต่ำ) อากาศยานจะปฏิเสธการลงจอด ไต่กลับขึ้น
เลื่อนเป้าออกไปก่อน แล้วภารกิจจะเข้าหาใหม่อีกหนึ่งครั้งถ้าเวลายังพอ
หลัง PX4 ยืนยันการแตะพื้น จะหน่วง 2 วินาทีให้นิ่งก่อนเซอร์โวปล่อยอย่างนุ่มนวล —
ถนอมไข่ ถ้า telemetry อ่านได้ว่ายังลอยอยู่ ณ จุดปล่อย การปล่อยจะถูก **ข้ามและบันทึก audit**

**ยุทธวิธีส่งซ้ำหลายเที่ยว** — ระหว่างเที่ยวบิน อากาศยานลงจอดที่จุด L&R และ disarm
เพื่อให้ทีมเติมสัมภาระเข้าอย่างปลอดภัย โหลดไข่ฟองใหม่ (และแบตเตอรี่ถ้าจำเป็น)
ผู้ควบคุมยืนยันหมายเลขเป้าหมายถัดไป แล้วปล่อยเที่ยวบินใหม่ นาฬิกากรอบ 20 นาที
เริ่มเดินที่ GO ครั้งแรก เกตต่อเที่ยวบินจะปฏิเสธการปล่อยเที่ยวบินที่จบไม่ทันกรอบเวลา
เว้นแต่ผู้ควบคุมยอมรับค่าปรับเวลาเกินอย่างชัดแจ้ง

## 3. การออกแบบและวิเคราะห์ทางวิศวกรรม (40 คะแนน)

### 3.1 โครงสร้างอากาศยานและความแข็งแรง

- **เฟรม:** quad-X บนโครง **Holybro X500 V2** ขนาด 500 มม. (แขนคาร์บอน deep-drawn +
  ดุมพอลิเมอร์ ~610 กรัม รวมฐานลงจอดทรงสูง รางแบตเตอรี่คู่ และแผ่นติดตั้ง RPi)
  ฐานลงจอดทรงสูงให้ระยะห่างพื้นแก่เปลไข่ตอนแตะพื้น และกันเซนเซอร์ flow/rangefinder
  ที่ชี้ลงพื้นให้พ้นภูมิประเทศ
- **ระยะห่างใบพัด:** มอเตอร์ข้างเคียงห่างกัน 354 มม. เหลือ **ระยะปลายใบพัด 100 มม.**
  สำหรับใบ 254 มม. (10″) — ใบพัดไม่ซ้อนทับ มาร์จินพอต่อการงอของแขน
  (เกณฑ์ DCOS: clearance-between-moving-parts)
- **ช่องบรรทุกสัมภาระ:** ออกแบบให้รับกล่องสัมภาระของผู้จัด V1.3 (ทรงหัวใจ
  ~16 × 7 × 18 ซม. กระดาษอาร์ต 300 แกรม พร้อมหูหิ้ว) — ไม่ใช่แค่ไข่เปล่า —
  โดยเซอร์โวปล่อยต้องไม่ติดกล่องตอนเปิด (รายการตรวจ fit-check บนโต๊ะที่ G5)
- **กรณีภาระโครงสร้าง:** ภาระการบินขณะหลบหลีก (จำกัด envelope ที่เอียง 35° /
  ความเร่งแนวราบ 3 ม./วินาที²), แรงกระแทกตอนลงจอดบนแท่น (รับโดยฐานทรงสูง +
  เปลยืดหยุ่นที่ `MPC_LAND_SPEED` = 0.3 ม./วินาที — ลำ 2.6 กก. มีพลังงานลงจอดมากกว่า
  แนวคิดเดิม 2.0 กก. ความยืดหยุ่นของฐาน/เปลจึงกำหนดขนาดตามนั้น), การขนย้าย และการเก็บรักษา
- **การกำหนดขนาดเส้นทางไฟ:** สายหลักซิลิโคน 10 AWG + XT90 (ต่อเนื่อง 90 A, พีค 150 A+)
  สำหรับ hover ~16 A / พีคเลวร้ายสุด ~110 A; สายเฟสมอเตอร์ 16 AWG (~40 A ต่อเส้น);
  power module แบบ Hall-effect พิกัด ≥150 A ขั้วต่อและสายไฟถูกยึดและมี strain relief;
  ชิ้นส่วนวิกฤตกันฝุ่น/ฝน (DCOS)
- **รายการที่ยังเปิดอยู่ (รายงานตามจริง):** **ตำแหน่งจุดศูนย์ถ่วง (CG)** และ
  **การวิเคราะห์ load factor / มาร์จินเชิงโครงสร้างแบบตัวเลข** ยังไม่ปิด —
  ทั้งคู่ถูก flag ไว้ในเอกสาร sizing และเป็นงานโต๊ะทดสอบที่ G5 (ตั้งทริม CG +
  ทดสอบภาระสถิต) โครงจริงยังต้องจูนใหม่ด้วย System-ID บนโต๊ะ (`tuning/`)
  เพราะความเฉื่อยสูงกว่าและความถี่ธรรมชาติต่ำกว่าโมเดล SITL; วงรอบ identify →
  synthesise → apply → re-validate ทั้งวงถูกทดลองใช้จริงครบวงจรแล้วใน SITL
  (การ identify 3 แกนได้ผลสะอาด และผลิตชุด gains ปัจจุบัน ยืนยันด้วย G4 run ในภาคผนวก ข.)

19.5 ม. (ต่ำกว่าค่าเคร่งครัด 20 ม. อยู่ 0.5 ม. เพื่อดูดซับความคลาดเคลื่อนของเฟรม
EKF/home ±0.7 ม.) และจุดปล่อยห่างศูนย์กลางแท่น 0.05–0.30 ม. ตลอดทุก G4 run ที่ commit ไว้

| GNSS | GPS แบบไม่มี RTK | หยาบ (~0.5–1.5 ม.); วิชันเป็นเจ้าของเมตรสุดท้าย |

กล้อง nadir ตัวเดียวเป็น **อำนาจควบคุมแต่เพียงผู้เดียว** — การถอดรหัสต้องการพิกเซลของมัน
และคิวตรวจจับแท่นขาว (white-pad cue) อยู่ในเฟรมเดียวกัน (ภาพขาวดำปลอดภัยต่อ detector:
การถอดรหัสทำงานบน grayscale อยู่แล้ว ส่วนคิวแท่นใช้ความสว่าง + ความเป็นสี่เหลี่ยม +
คอนทราสต์กึ่งกลางเข้ม) global shutter ตัดการเบลอ/เบี้ยวของภาพที่ความเร็วกวาด 10 ม./วินาที
การฉายพิกเซล → พิกัดพื้น ประกอบท่าทางอากาศยานเข้าไปในสมการ พร้อม median filter และ
เกตกรองเฟรมเอียง (tilt-gate) เพื่อตัดเฟรมที่สัญญาณรบกวนสูงสุด (ตอนเอียงเลี้ยว) ทิ้ง

### 3.4 สถาปัตยกรรมซอฟต์แวร์ — โหมดทำงานและระบบความปลอดภัย

สแต็กระบบอัตโนมัติเป็นระบบ **deterministic, offline, classical** บน CM4
(Python 3.12, async) ไม่มี LLM ไม่มีคลาวด์ ไม่มีเครือข่ายระหว่างบิน
(การใช้เครือข่าย = ตัดสิทธิ์อัตโนมัติ) แบ่งชั้นดังนี้:

- **Mission orchestrator** (`orchestrator/mission.py`) — state machine ต่อเที่ยวบินตาม
  §2.3 ขับเคลื่อนด้วยเกต preflight GO ต่อเที่ยวบิน; โปรเซสเดียวรันยาวบินครบทุกเที่ยวบิน
  ตลอดกรอบเวลา
- **Vision worker** (`orchestrator/vision_worker.py`) — ถอดรหัส ArUco จากกล้อง nadir +
  คิวก้อนแท่นขาว ป้อนทะเบียนแท่นที่จัดเก็บตามหมายเลข marker พร้อมยืนยันแบบ k-vote
- **ตัวควบคุมช่วงปลาย** (`orchestrator/tactical_align.py`) — เกตร่อนลงเป็นขั้นแบบ
  land-ON, เกต id-verified LAND, เกตเล็งกึ่งกลางขั้นสุดท้าย (ขั้นสุดท้ายที่ไม่ล็อก
  จะเลื่อนออกแทนที่จะลงจอด) และการปล่อยแบบ touchdown-gated
- **Safety watchdog** (`orchestrator/safety.py`) — มอนิเตอร์พื้นหลัง 2 Hz (ด้านล่าง)
- **GCS** — Svelte dashboard แบบกระชับ: แผนที่สด (วาดเส้นทาง transit + เขตห้ามบิน),
  ภาพกล้อง, ตัวแก้ไขคิวภารกิจ 4-จาก-6 แบบเรียงลำดับ + GO ต่อเที่ยวบิน,
  จอสรุปแท่นที่ยืนยันแล้ว (หมายเลข + พิกัดที่ได้ — รายการคะแนนของกติกา) และปุ่ม KILL ฉุกเฉิน

**โหมดทำงาน:** PREFLIGHT (รอ GO ต่อเที่ยวบิน) · TAKEOFF · TRANSIT_INGRESS ·
SEARCH · LOCALIZE · LAND · DROP · TRANSIT_EGRESS · RTH · ABORT

**ระบบความปลอดภัย (มาตรการ fail-safe ตาม DCOS "fail-safe operating mode"):**

*Watchdog ฝั่ง companion (2 Hz, รู้จัก phase):*
- หลุด geofence → Return-to-Home; เข้าเขตห้ามบิน → RTH
- เพดานความสูง: โผล่เกิน 20.5 ม. ชั่วครู่ → บันทึก anomaly; ค้างเกิน 22 ม. → RTH
- คำเตือนเพดานล่างช่วงค้นหา: ต่ำกว่า 10 ม. นอก phase ร่อนลงส่งของ → บันทึก anomaly
- ขาด GPS 3D-fix (มี debounce) → RTH; ขาด datalink (มี debounce) → บินออกฉุกเฉิน
- แบตเตอรี่: < 30 % → RTH, < 20 % → LAND ณ จุดนั้น; สตรีมค่าแบตเตอรี่เป็น **NaN ต่อเนื่อง**
  (เซนเซอร์หลุด) จะยกระดับเป็น anomaly เสียงดังถึงผู้ควบคุม แทนที่จะปิดการป้องกัน
  แบตเตอรี่แบบเงียบ ๆ
- **ตัวป้องกันภาพค้างระหว่างบิน (camera-freeze guard)** — ตัวเขียนภาพ publish เฟรม
  ด้วย atomic replace ดังนั้นถ้าตัวเขียนตาย ภาพสุดท้ายจะค้างอยู่บนดิสก์ และตัวอ่านแบบไร้เดียงสา
  จะ "เห็น" แท่นเก่าไปเรื่อย ๆ — ทั้ง vision worker และตัวควบคุมช่วงปลายจึงปฏิเสธเฟรม nadir
  ที่เก่ากว่า 2 วินาที กล้องพังระหว่างร่อนลงจึงอ่านผลเป็น *ไม่พบเป้า* (เข้าเส้นทางไต่กลับ/
  เลื่อนออก) และไม่มีทางผ่านเกต LAND ด้วยภาพแช่แข็ง

*Failsafe ระดับ flight controller (ทำงานแม้ companion ตาย — pin ค่าและอ่านกลับตรวจสอบ
ตอนเริ่มภารกิจ):*
- `NAV_DLL_ACT` = Return (ขาด datalink), `GF_ACTION` = RTL (หลุด geofence),
  `NAV_RCL_ACT` = Return (ขาดลิงก์ RC / นักบินนิรภัย พร้อม `COM_RCL_EXCEPT`
  เพื่อไม่ให้เที่ยวบินอัตโนมัติที่ไม่ใช้ RC ถูกสั่งกลับโดยไม่จำเป็น) และเกณฑ์แบตเตอรี่
  (`BAT_LOW/CRIT/EMERGEN_THR` + `COM_LOW_BAT_ACT`) ที่ตั้งไว้ต่ำกว่าชั้น 30/20 %
  ของ companion เพื่อไม่ให้สองชั้นแข่งกัน
- `RTL_RETURN_ALT` = 20 ม. เพื่อให้ RTL จาก failsafe ใด ๆ ยังถูกกติกาที่เพดานบิน
  (ค่า default ของ PX4 คือ 60 ม. ซึ่งทะลุเพดาน)

*อินเตอร์ล็อกฝั่งสถานีภาคพื้น:*
- ปุ่ม **KILL** ฉุกเฉินที่ตัดมอเตอร์ทันที รวมถึงคำสั่ง arm/disarm — ทั้งหมดคุ้มกันด้วย
  arm session ของช่องคำสั่ง และ CSRF header โดยคำสั่งทำลายล้างจะ auto-disarm session
  เพื่อกันการยิงซ้ำโดยบังเอิญ
- คำสั่ง **DROP** ด้วยมือถูกล็อกด้วยเงื่อนไขแตะพื้นเช่นเดียวกับเส้นทางอัตโนมัติ:
  ถูกปฏิเสธเมื่อ telemetry อ่านได้ว่ายังลอยอยู่ (เว้นแต่ผู้ควบคุม force อย่างชัดแจ้ง)
  ไข่จึงไม่มีทางถูกปล่อยจากที่สูงเพราะคลิกพลาด

**การบันทึกและส่งภาพ (กติกา V1.3)** — ระบบ *ส่ง* ภาพสดไปยัง GCS และ *บันทึก*:
JPEG trail อัตราต่ำ (~1 Hz จากกล้อง nadir) ถูกเก็บถาวรต่อภารกิจใน `runs/<id>/frames/`
นอกเส้นทางวิกฤตการบิน (ตัวบันทึกล้มเหลวเป็นแค่คำเตือน ไม่มีวันทำภารกิจล่ม)

**หลักฐานความสมบูรณ์ของซอฟต์แวร์** — แกนการบินมีการทดสอบอัตโนมัติ 239 รายการ
(unit + integration) ที่ import โมดูลจริง — mission loop, ตัวควบคุมช่วงปลาย, watchdog,
detector, คณิตการฉายพิกัด — ผ่านทั้งหมด พร้อม static type-checking และ lint สะอาด
การแก้พฤติกรรมทุกครั้งขับเคลื่อนด้วยการเขียนเทสก่อน (test-driven); เกต G4 ใน SITL
ทดสอบลำดับทั้งหมดครบวงจร (ภาคผนวก ข.) นอกเหนือจากชุดเทส ทีมยังทดสอบ workflow
ผู้ควบคุมครบวงจรด้วยการขับ GCS จริงผ่านเบราว์เซอร์ตลอดภารกิจ SITL หลายเที่ยวบิน;
จุดบกพร่องเชิงปฏิบัติการ 2 รายการที่พบ (ทางลัด override ของผู้ควบคุมที่เข้าไม่ถึง
เมื่อเวลาเหลือน้อย และ timeout ของขั้นร่อนที่หลุดไปลงจอดแบบเยื้องศูนย์)
ถูกแก้ ล็อกด้วย regression tests และทวนสอบซ้ำในการบินแล้ว

### 3.5 กลไกจัดการสัมภาระ

เซอร์โวตัวเดียวบนช่อง **AUX 9** ของ flight controller ควบคุมตัวยึดไข่:
PWM **1900 µs = ปล่อย**, **1100 µs = ยึด** (การแมปแบบ bipolar คร่อมจุดกึ่งกลาง
เพื่อให้เซอร์โวข้ามตำแหน่งจริง) กลไกปล่อยหนึ่งชุด → ไข่หนึ่งฟองต่อเที่ยวบิน
(`payload_id` = 0 เสมอ); กติกาห้ามปล่อยหลายสัมภาระพร้อมกันและห้ามใช้วินช์ —
เคารพทั้งสองข้อ เปลไข่เป็นโฟม/TPU พิมพ์ 3 มิติแบบยืดหยุ่น (งบมวลไข่ + เปล
**80–120 กรัม**, ใช้ 100 กรัมใน mass rollup) ที่ดูดซับแรงแตะพื้นและเปิดออกด้วย
แรงโน้มถ่วงเมื่อเซอร์โวปล่อย การปล่อยถูก **ล็อกหลังยืนยันแตะพื้น** (หน่วงนิ่ง 2 วินาที)
และเป็น idempotent ต่อเที่ยวบิน (มี ledger กันปล่อยซ้ำข้ามการ retry)
ตาม DCOS สัมภาระถูกยึดแน่นตลอดการบินและกลไกไม่มีพฤติกรรมที่ไม่ปลอดภัย

### 3.6 ระบบสื่อสาร

- **Telemetry / C2:** datalink ระยะ ≥ 500 ม. line-of-sight ในย่านที่แนะนำ
  (**920–925 / 2400–2500 / 5725–5850 MHz**) — **ไม่ใช้ 4G LTE / SIM** (ต้องห้าม)
- **RC นักบินนิรภัย:** ELRS (ระยะไกล ย่าน 2.4 GHz ที่แนะนำ)
- **ภาพ:** CM4 ส่งต่อภาพกล้องไปยัง GCS และจอแสดงผลภายนอก ≥ 1 จอสำหรับกรรมการ ตามกติกา
- **การกำหนดเส้นทางบนบอร์ด:** mavlink-router กระจายลิงก์การบินให้ orchestrator
  (offboard), dashboard และ QGroundControl ภาคพื้น (ตัวเลือก) โดย endpoint ของ QGC
  **default เป็น loopback** — จะเปิดให้โฮสต์ภาคพื้นเฉพาะโดยเจตนาเท่านั้น
  ระนาบควบคุม MAVLink ของอากาศยานติดอาวุธจึงไม่ถูกเปิดแบบไร้การยืนยันตัวตน
  บนเครือข่ายสนาม

### 3.7 ขั้นตอนปฏิบัติ (ปกติและฉุกเฉิน)

**ปฏิบัติการปกติ:** ผู้ควบคุมป้อนหมายเลขที่กรรมการกำหนดครั้งเดียวเป็นคิวภารกิจ
แบบเรียงลำดับ (สูงสุด 4 จาก 6 หมายเลข) จากนั้นต่อเที่ยวบิน: บอร์ดความพร้อม preflight
เขียวครบ (ลิงก์, พร้อม arm, EKF, home, เซนเซอร์, GPS fix, แบตเตอรี่, อยู่พื้น, geofence,
กล้องสด) → ผู้ควบคุมยืนยันโหลดไข่แล้ว → GO (หมายเลขแท่น resolve จากคิว;
เลือกด้วยมือ override ได้หนึ่งเที่ยวบิน) → เที่ยวบินอัตโนมัติ → ลงจอด + disarm ที่ L&R →
เติมสัมภาระ → วนซ้ำ นาฬิกากรอบเวลาและเกตงบเวลาต่อเที่ยวบินบริหารตาราง
4 เที่ยวบิน/20 นาที; เกตจะปฏิเสธการปล่อยที่จบไม่ทันกรอบ เว้นแต่ผู้ควบคุม force
อย่างชัดแจ้งเพื่อยอมรับค่าปรับเวลาเกิน (บอร์ดความพร้อมแสดงเวลาที่เหลือน้อยเป็น
คำแนะนำ (advisory) เพื่อให้ทาง override ของผู้ควบคุมยังเข้าถึงได้เสมอ)

**ปฏิบัติการฉุกเฉิน:** นักบินนิรภัยเข้าควบคุมด้วยมือได้ทุกเมื่อ; ปุ่ม KILL ของ GCS
ตัดมอเตอร์ทันที failsafe อัตโนมัติ (watchdog ฝั่ง companion + RTL ระดับ FC เมื่อ
geofence/datalink/RC/แบตเตอรี่ผิดปกติ) กู้คืนหรือนำอากาศยานลงจอดโดยไม่ต้องมีคนสั่ง
เมื่อเกิด error ที่ไม่ได้รองรับใน mission loop ระบบ orchestrator จะสั่ง RTH→LAND ฉุกเฉิน
และปล่อยให้ failsafe ของ FC รับช่วงต่อ ทีมสามารถกลับมากลางกรอบเวลาและเริ่มเที่ยวบินใหม่
โดยไม่เสียค่าปรับตราบใดที่กรอบเวลายังไม่หมด
